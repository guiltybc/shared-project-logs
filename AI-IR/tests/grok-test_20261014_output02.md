# AI-IR Receiver Review 02
## 受信側LLM（Grok）による独立設計レビュー

**本レビューの位置づけ**  
本出力は設計レビューであり、実測テストではない。ChatGPTの提案を正しい前提とは扱わず、独立に評価する。受信側の記憶能力を過大評価しない。定義の復唱能力と実際のPAYLOAD解釈能力を区別する。自分の提案についても副作用を指摘する。不明な契約内容を推測で補完しない。

---

### AGREED

- **情報の身分区別の維持**（REQUEST 4の中核）  
  FACT / CLAIM / INFERENCE / HYPOTHESIS / EVALUATION / UNKNOWN の区別を維持することに同意する。送信側がFACTと記載したことは、受信側が独立に事実確認したことを意味しない、という明示も必要かつ有用である。

- **構文追加の最小化**（REQUEST 5）  
  新構文は「具体的な誤読リスクを減らせること」で評価し、単なる便利さでは追加しない方針に同意する。

- **AI-IRと外部ログの役割分担**（REQUEST 2関連）  
  AI-IR自体に完全な履歴管理機構を組み込まず、過去の送信内容の保存は外部ログに委ねる役割分担に賛成する。AI-IRは「現在の状態と、その更新の意味」を伝えればよい。

- **`?` の意図の方向性**  
  「FACTとして確定していない。受信側が勝手に昇格させない」という方向性は適切。無理に「未確認・真偽不明・情報不足」を同一状態にまとめない点も良い。

### DISAGREED

- **CORE CONTRACTの二層構造を標準とする案**（第3節）  
  現時点では不要と判断する。PAYLOAD自体が初見で身分を保持できる記法であれば、毎回または定期的にCORE CONTRACTを共有する二層は、通信量と運用複雑性を増やすだけである。CORE CONTRACTが存在しない状態でも、PAYLOADだけで解釈可能であることを優先すべき。

- **契約ID（CONTRACT:AI-IR-C01）の新設**  
  識別子を認識できることと、内容を正しく復元できることは別である。契約IDだけでは定義を復元する保証はなく、むしろ「IDがあるから契約を知っている」という誤った安心感を生む。既存のUNIT / REFや、必要時の自然言語再送要求で代替可能。

- **NOTEをPATCHの標準注記として採用すること**  
  サンプルの `NOTE|I1の対象範囲を精密化` は初見で理解可能だが、NOTEがPATCH全体にかかるのか、特定の削除・追加項目にかかるのかが曖昧。訂正理由と訂正内容の混同リスクがある。

### MODIFY

- **対象共有（REQUEST 1）**  
  既存のUNIT / REFで多くの場合は足りる。同じプロジェクト内の異なる出来事を区別する場合、自然言語による対象指定（例: 「契約終了通知」）を文中に残すことで十分。新アンカーは、具体的な誤読事例が複数確認されてから検討する。現時点では追加不要。

- **PATCH訂正の表現（REQUEST 2）**  
  `NOTE` を固定構文とするのではなく、削除・追加行の直後に自然言語で短く添える運用を推奨。  
  例:  
  ```text
  @PATCH U21:PROJECT
  -I1|契約終了:突然
  +I2|契約終了通知:突然  # I1の範囲を通知に限定して精密化
  +I3|事前交渉:存在
  ```  
  I1からI2への置換関係を明示する専用構文は不要。自然言語で足りる。置換関係の明示を強制すると、軽量性が損なわれる。

- **主要記号の定義範囲（REQUEST 3）**  
  `?` については一行定義を採用方向でよい。ただし `CLM / I / SRC / <-` については、初見で意味が通じる限り定義を省略してよい。定義を追加しすぎると、かえって「定義に書いていない用法は禁止」と解釈が狭まる副作用がある。

### MINIMUM CONTRACT

受信側として最低限必要な意味上の約束は以下に限る。これらは「毎回添付」ではなく、必要時に再確認可能な短い文言とする。

- 情報の身分（FACT / CLAIM / INFERENCE 等）を無断で変更しない。
- UNKNOWN および `?` を勝手にFACTへ昇格しない。
- CLAIMを検証済みFACTとして扱わない。
- 送信側がFACTと記載したことは、受信側の独立検証を意味しない。
- PATCHは現在状態の更新であり、過去に送信した内容の存在自体を消去するものではない（外部ログが履歴を保持する）。

これ以上をCORE CONTRACTとして固定化する必要はない。

### CONTRACT RETENTION POLICY

推奨は **方式D（必要時に確認）を基本とし、方式E（重要な通信前）と組み合わせる** こと。

- 新規セッション開始時：最低限のMINIMUM CONTRACTを自然言語で1回共有する。
- 通常の情報交換中：再掲しない。
- 受信側が「このPAYLOADの身分解釈に確信が持てない」と判断した場合：自然言語で「CORE CONTRACTを再送してほしい」と要求する。
- 重要な意思決定や長期にわたる状態更新の直前：送信側が任意でMINIMUM CONTRACTを再掲する。

方式A（毎回全文）は通信量を増やしすぎる。方式B（初回のみ）は長期会話・新規セッションで破綻する。方式C（定期）は確認間隔中の誤読を防げない。

契約IDは使用しない。再送要求は自然言語で十分であり、専用構文は不要。

### COMMUNICATION COST

- MINIMUM CONTRACTの自然言語再送：1回あたり数行。頻度を「必要時のみ」に抑えれば、圧縮効果を上回るコストにはならない。
- 副作用：受信側が「再送を要求すべきタイミング」を見逃す可能性。これを完全に機械的に防ぐ仕組みは軽量性を損なうため、受け入れない。
- 二層構造や契約IDを常時運用すると、通信量が確実に増加し、かつ「契約が共有されている」という錯覚を生む。

### OPEN ISSUES

- 長期会話やコンテキスト圧縮後に、受信側がMINIMUM CONTRACTをどれだけ保持できるかは未検証。
- 「重要な通信」の判断基準をどう共有するか。
- 受信側が再送要求を出さずに誤読を続けるリスクを、どの程度まで許容するか。
- `?` の一行定義が、実際の異なるLLMで同じように解釈されるか。

### RECEIVER RESPONSE 02

**ChatGPTへの変更要求**

1. CORE CONTRACTの二層構造を標準仕様とせず、PAYLOAD優先とする。MINIMUM CONTRACTは必要時の自然言語再送に限定する。
2. 契約IDを新設しない。
3. PATCHの注記は `NOTE` 固定構文ではなく、自然言語のインライン注記を許容する運用とする。
4. `?` については「FACTとして確定していない。昇格させない」という一行を採用方向でよい。他の記号は初見理解を優先し、定義を強制しない。
5. 対象共有は既存UNIT / REFと自然言語表現で対応し、新アンカーは追加しない。
6. 再送要求は自然言語で行い、専用構文を作らない。
7. 上記を前提に、実測テスト（TEST 41相当）を設計・実施する段階に進むことを推奨する。設計上の合意をこれ以上広げない。
