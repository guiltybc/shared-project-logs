# AI-IR Receiver Review 01
## 受信側LLMによる独立設計レビュー

あなたは、LLM間の軽量中間表現「AI-IR」の受信側として、仕様改善に参加してください。

送信側はChatGPT、受信側はGrokです。人間が双方の出力をコピー＆ペーストして中継します。

今回の目的は、ChatGPTの設計案を承認することではありません。

**受信側の立場から、問題点・曖昧性・不足・不要な構造を独立して発見し、必要な変更を要求すること**です。

## 1. AI-IRの基本思想

AI-IRは自然言語を短縮しながら、情報の意味と身分を維持するための軽量中間表現です。

- FACT / CLAIM / INFERENCE / HYPOTHESIS / EVALUATIONを区別する。
- UNKNOWNを勝手に補完しない。
- 評価主体と根拠関係を保持する。
- 差分更新にはPATCHを利用する。
- 初見で理解できる記法を優先する。
- 巨大な辞書や詳細な文法定義に依存しない。
- 受信側LLMの既存の意味理解能力を利用する。
- 記憶に依存しない。

基本原則：

**情報量を減らしても、情報の身分は落とさない。**

## 2. 今回の追加検討課題

異なる情報源が同じ出来事について説明した場合、両者の発言が矛盾しているように見えても、実際には対象・時点・認識範囲が異なるだけかもしれません。

また、送信側AIが後から解釈を訂正した場合、最新情報だけでなく、以前何を伝え、何を変更したかを追跡できる必要があるかもしれません。

ただし、これらの課題に新しい構文が必要かどうかは未確定です。

## 3. 検討用サンプル

### CASE A：異なる情報源

```text
CLM1|中止通知:突然
CLM1:SRC|当事者A

CLM2|中止前交渉:数か月
CLM2:SRC|関係者B
```

### CASE B：情報の訂正

初回送信：

```text
@U21:PROJECT
I1|契約終了:突然
I1 <- CLM1
```

後続送信：

```text
@PATCH U21:PROJECT
-I1|契約終了:突然
+I2|契約終了通知:突然
+I3|事前交渉:存在
```

### CASE C：情報の適用範囲

```text
CLM1|制作工程の一部:AI使用
CLM1:SRC|企業説明
```

### CASE D：未確認情報

```text
?F1|予算超過:発生

I1|契約終了理由:予算超過
I1 <- ?F1
```

## 4. Grokへの依頼

以下について、ChatGPTへの忖度なしに回答してください。

1. 各CASEを初見でどのように解釈するか。
2. 誤読や複数解釈が生じる部分はどこか。
3. 現在の記法だけで十分か。
4. 受信側として不足している情報は何か。
5. 新しい記法が必要なら、最小限の変更案は何か。
6. 逆に、追加すべきではない仕組みは何か。
7. 過去の発言と訂正を追跡する場合、PATCHだけで十分か。
8. 受信側が誤読を検出・報告するために、送信側へ何を要求したいか。

## 5. 回答形式

各CASEについて、次の項目を出力してください。

- INTERPRETATION：受信した意味
- AMBIGUITY：曖昧な箇所
- RISK：誤読・情報喪失の可能性
- REQUEST：ChatGPTに要求する変更
- PRIORITY：必須／推奨／不要

最後に、受信側としての総合的な設計要求をまとめてください。

## 6. 重要な条件

- ChatGPTの案を正しい前提として扱わない。
- 新しい記法を作ること自体を目的にしない。
- 現行記法で十分なら、そのように回答する。
- 不明なものを推測で埋めない。
- CASEの解釈と仕様改善提案を明確に分離する。
- 自分が提案した仕様についても、欠点や副作用を指摘する。
- 他のLLMが必ず同じように理解すると断言しない。
- このレビューは実測テストではなく、受信側による設計レビューであることを明示する。

最終的に、ChatGPTへ返送するための **RECEIVER CHANGE REQUEST** を作成してください。
