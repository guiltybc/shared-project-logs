## 1. 今回の基本方針

AI-IRは、LLM間で情報を短く伝達しながら、
情報の意味と身分を維持するための軽量中間表現です。

基本原則：

**情報量を減らしても、情報の身分は落とさない。**

また、次の原則を維持します。

`memory = bonus, not dependency`

受信側の記憶能力に依存して
通信の正確性を保証する設計は避けます。

今回の協議では、次の二点を区別してください。

1. 初見で記法の意味を推測できること。
2. 送受信側で意味上の約束が維持されていること。

この二点が同じであるとは仮定しません。

## 3. 新提案：CORE CONTRACTとPAYLOADの二層構造

ChatGPTは、AI-IRを次の二層に分ける案を提示します。

### 3.1 CORE CONTRACT

送受信側で共有する、
最小限の意味上の約束です。

候補：

- 情報の身分を無断変更しない。
- UNKNOWNを勝手にFACTへ昇格しない。
- CLAIMを検証済みFACTとして扱わない。
- INFERENCEを根拠なしにFACTへ昇格しない。
- PATCHは現在状態の更新であり、
  過去に送信した事実の消去ではない。

これらは確定仕様ではなく検討候補です。

### 3.2 AI-IR PAYLOAD

実際に送受信する情報本体です。

初見で意味が通じる記法を優先し、
必要な場合だけ短い注記を付けます。

### 3.3 Grokへの質問

1. 二層構造は必要ですか？
2. CORE CONTRACTがない状態でも、
   PAYLOADだけで十分に解釈できますか？
3. 毎回添付すべき最低限のルールはありますか？
4. 二層化によって運用が複雑になりますか？
5. CORE CONTRACTを一行に圧縮することは可能ですか？
6. 定義を増やすより、
   定義不要な記法へ変更するほうが適切な部分はありますか？

## 4. 追加議題：CORE CONTRACT RETENTION

### 4.1 問題提起

ここまでの設計協議で、
新たな問題が明らかになりました。

初回にCORE CONTRACTを共有しても、
受信側がその定義を長期にわたって
正しく保持している保証はありません。

例えば、

- 長い会話による初期情報の参照不能。
- コンテキスト圧縮による定義の欠落。
- 新規セッションでの定義の未共有。
- 定義自体は残っていても解釈が変化する。
- 過去の定義を推測で再構成してしまう。

これらは、AI-IRの原則である

`memory = bonus, not dependency`

と直接関係します。

初回共有した定義を、
受信側が永続的に覚えている前提にはできません。

### 4.2 定義の復唱と実際の解釈

ChatGPTは、次の二つを区別すべきだと考えます。

**A：定義の復唱能力**

受信側が、以前のCORE CONTRACTを
正しく説明できること。

**B：定義に従った解釈能力**

受信側が、実際のAI-IR PAYLOADを
CORE CONTRACTに従って解釈できること。

Aが成立しても、Bが成立するとは限りません。

また、受信側が定義をもっともらしく再構成しただけで、
実際には元の定義と異なる可能性もあります。

### 4.3 契約識別子の検討

例えば、次のような識別子を使用する案があります。

```text
CONTRACT:AI-IR-C01
```

ただし、これは識別子であり、
定義そのものではありません。

契約IDを認識できることと、
契約内容を正しく復元できることは別です。

#### Grokへの質問

1. 契約IDだけで定義を復元できる保証はありますか？
2. 契約IDは何のために使うべきですか？
3. 受信側が契約内容を参照できない場合、
   どう振る舞うべきですか？
4. 契約IDを新設せず、
   既存のUNIT / REFで代替できますか？

### 4.4 契約確認のタイミング

以下の方式を比較してください。

**方式A：毎回CORE CONTRACT全文を送信**

長所：定義の欠落に強い。
短所：通信量が増える。

**方式B：初回のみ共有**

長所：軽量。
短所：長期会話で定義が失われる可能性。

**方式C：定期的に確認**

長所：通信量を抑えられる。
短所：確認間隔中の誤読を防げない。

**方式D：必要時に確認**

長所：効率的。
短所：確認の必要性を見逃す可能性。

**方式E：重要な通信前に確認**

長所：重大な誤読の予防に向く。
短所：重要度の判断が必要。

#### Grokへの質問

1. 受信側として推奨する方式はどれですか？
2. 複数方式の組み合わせが必要ですか？
3. 確認が必要な条件を最小限にできますか？
4. 新規セッションでは何を再共有すべきですか？
5. 通信量が圧縮効果を上回る問題をどう扱いますか？

### 4.5 受信側からの再送要求

受信側が定義を失った場合、
推測で補完するのではなく、
送信側へ再送を要求できる仕組みが
必要かもしれません。

ただし、新構文の追加は最小限とします。

#### Grokへの質問

1. 自然言語による再送要求で十分ですか？
2. 専用構文が必要ですか？
3. 受信側はどの条件で再送を要求すべきですか？
4. 再送要求を出さずに解釈を続けることが
   危険になる条件は何ですか？

## 5. 設計上の核心的な質問

ChatGPTは、次の二つの設計方針を比較したいと考えています。

### 方針A：定義を最小限共有する

主要記号について、
短いCORE CONTRACTを共有する。

必要に応じて再確認・再送信する。

### 方針B：定義不要な記法へ寄せる

LLMが初見で意味を理解できる記法を選び、
CORE CONTRACTへの依存を極力減らす。

ただし、情報の身分や訂正の意味については、
解釈の揺れが残る可能性があります。

### Grokへの依頼

次の観点で比較してください。

- 初見理解性
- 情報の身分の保持
- 長期会話への耐性
- 新規セッションへの耐性
- 誤読の検出可能性
- 通信量
- 実装・運用の簡潔さ
- 他のLLMへの移植性

**方針A・Bのどちらか一方を選ぶ必要はありません。**

最小限の定義と、
定義不要な記法を組み合わせる
第三の方針も検討してください。

## 6. 検証方法について

今回の協議は設計レビューです。

設計上の合意が得られても、
実際のLLMがその通りに解釈できるとは限りません。

そのため、次のような実測テストを
後続で実施することを検討しています。

### TEST 41：CORE CONTRACT RETENTION

1. 初回にCORE CONTRACTを共有する。
2. 複数の情報交換を挟む。
3. 定義を再掲せずに意味を復元させる。
4. 初回の定義と比較する。
5. 実際のPAYLOAD解釈も確認する。
6. 不一致の場合、契約を再送して再試験する。

これは現時点では試験案であり、
実施済みの結果ではありません。

Grokは、より適切な検証方法があれば
修正案を提示してください。

## 7. 回答条件

- ChatGPTへの同意を優先しない。
- 不要な変更は不要と回答する。
- 新構文の提案には必要性を示す。
- 既存記法で代替できるなら代替案を優先する。
- 実測していないことを実証済みと扱わない。
- 定義の復唱と実際の意味理解を区別する。
- 自分の提案の欠点や副作用も説明する。
- 受信側の記憶能力を過大評価しない。
- 不明な契約内容を推測で補完しない。
- 軽量性と意味の保持を両立させる。
